# Upstream and distributed artifacts

## What this flake authored

This grant covers this flake's own expressions: `flake.nix`, `pin.nix`, `README.md`, and this file. That is the expression that names an upstream image by registry, repository, release and manifest digest, and the record of the hash that verifies the copy it builds. The selection is ours, and nothing in it is a derivative of the image it pins — an expression that binds upstream by name and digest, and fetches nothing until a build asks for it, copies none of the work it names.

The two files under `.github/workflows/` are not our expression. They are generated from [flake-lib](https://github.com/jgus-org/flake-lib) templates and rewritten on this repository's version branches by flake-lib's own updater, which also rewrites `pin.nix` there. flake-lib carried no license file at the revision this flake locks (`e102eb2e5b3f958e8bf23695e60215dcbfc89bfd`), so no terms are stated by the source those files come from; that is a gap in flake-lib, and it is being settled there rather than assumed here.

## What the pinned image carries

`packages.image` is not a name for upstream bytes, it is a copy of them. [flake-lib's `mkOciImage`](https://github.com/jgus-org/flake-lib/blob/e102eb2e5b3f958e8bf23695e60215dcbfc89bfd/lib/mk-oci-image.nix) builds it as a fixed-output derivation that runs `skopeo --insecure-policy copy --preserve-digests --tmpdir "$TMPDIR" --src-tls-verify=true docker://ghcr.io/home-assistant/home-assistant@sha256:c32ab33f0b0589182b2f40324826acb02a104d1707c91573b6420fd622b82127 dir://$out`, so the output is a Skopeo `dir:` layout holding the platform manifest, the runtime configuration and the compressed layers exactly as published — 22 layers, 659,349,865 bytes compressed, each `application/vnd.oci.image.layer.v1.tar+zstd`, no archive conversion and no rewritten layer. The pinned digest is the `linux/amd64` manifest inside the OCI index that `ghcr.io/home-assistant/home-assistant:2026.10.3` names, and `pin.nix` holds that digest with the recursive Nix hash `sha256-XkWzgAHcciK7CwC3fDH4cz5W5/DP33BBR6ZWutCuA1g=` of the resulting directory. `copyTo` and `copyToPodman` re-copy that directory with `--preserve-digests`, so the bytes leave the store as they arrived.

That index (digest `sha256:407b89cd11a8cb67d388d21739a226c74acbbebe1ac59e3b83b11b43ce76b98f`) has four entries, two of which are platforms: the pinned `linux/amd64` manifest and `linux/arm64` (`sha256:c2bb99de7179fe0c192757bc70a53db5f2ded6672a1ced0007accccd3f0de44c`). The other two carry `platform` of `unknown/unknown` and are not platforms at all — each is an OCI manifest with `artifactType` `application/vnd.docker.attestation.manifest.v1+json`, a single `application/vnd.in-toto+json` layer annotated `in-toto.io/predicate-type` `https://slsa.dev/provenance/v1`, and a `subject` naming one of the two platform manifests. They are the build's SLSA provenance attestations, published beside the image. Because this flake pins one platform manifest, its output carries that manifest and its layers and not the attestation that sits next to it in the index; a recipient who wants the provenance statement pulls it from the registry by its own digest.

Everything below is what those bytes contain. It is established from the image's own manifest and configuration blob and from the upstream recipes that produced it; no layer was unpacked, so this is an account of what upstream's build records, not an inventory of the filesystem.

### Home Assistant Core

[Home Assistant Core](https://github.com/home-assistant/core) is Apache-2.0: its [`LICENSE.md` at the `2026.10.3` tag](https://github.com/home-assistant/core/blob/2026.10.3/LICENSE.md) is the canonical Apache-2.0 text, and its `pyproject.toml` declares `license = "Apache-2.0"` with `license-files = ["LICENSE*", "homeassistant/backports/LICENSE*"]` — that second path is the PSF text covering the backported standard-library code, and those two are the only license texts in the tree — the recursive listing at the pinned tag matches a third name, `script/licenses.py`, which is upstream's own tool for checking dependency licenses rather than a license. Those files travel inside the image: its history shows the source copied to `/usr/src/homeassistant` and installed with `uv pip install -e ./homeassistant`, and the same history copies `LICENSE*` and `pyproject.toml` into that tree, so the license texts arrive in the installed distribution metadata. Apache-2.0 §4(a)'s duty to give recipients the license is therefore discharged inside the image, not here. Upstream's own `org.opencontainers.image.licenses` label on the manifest reads `Apache-2.0`; that describes Home Assistant Core, and the sections below are what else is in the image besides it.

### The Python environment

The core layer installs two requirement files under the in-image paths `homeassistant/requirements.txt` and `homeassistant/requirements_all.txt`, which are the tag's root `requirements.txt` and `requirements_all.txt` copied into `homeassistant/` by the build, and home-assistant/docker's own root `requirements.txt` is installed in the base stage by a build-time mount. We read that third file at that repository's tag `2026.10.1`: `home-assistant/docker` publishes no tag at or above that — its tag list stops at `2026.10.1` — and its `BUILD_FROM` default is the same base image the pinned layers record, which is what ties the recipe to this image. That file names three distributions, `Brotli`, `mysqlclient` and `psycopg2`, and its pins are in the set below. Parsing those three files for `name==version` pins, keeping an extras clause such as `yt-dlp[default]` attached to its name, normalizing case and the `_`/`.`/`-` separators, and de-duplicating across files gives 1,192 distinct pinned distributions: 54 pinned names from the root `requirements.txt` plus 1,156 from `requirements_all.txt`, less the 21 names both files pin, plus the three from docker. Four more names in the root file — `certifi`, `packaging`, `typing-extensions` and `urllib3` — are bounded by range rather than pinned, so the version installed for each is whatever the build resolved and they are not counted. `homeassistant/package_constraints.txt`, which the build also copies in, is a constraint file and not an install input, so it is out of the count; `home-assistant-frontend` and `home-assistant-intents` are pinned in `requirements_all.txt` and installed by wheel filename, so they are in the set once.

We then read each distribution's own declaration from PyPI at its pinned version — the `license_expression` field where the distribution publishes one, otherwise its license classifiers, otherwise the deprecated free-text `license` field — and counted each distribution once, under the strongest copyleft its declaration states or under its permissive term when it states none. Of the 1,192, 298 publish a machine-readable expression, 690 declare through a classifier, 189 publish nothing but free text, and 15 publish nothing in any field. By that reading: MIT 734, Apache-2.0 264, the GPL family 80, the BSD family 43, the LGPL family 28, other permissive terms 15, nothing declared 15, MPL-2.0 4, the AGPL family 4, ISC 3, one declaring only a proprietary license, and one whose declaration is the setuptools placeholder `Type license() to see the full license text` (`maxcube-api==0.4.3`), which declares nothing despite filling the field. These are the projects' own claims at those versions, and some of them are stale or wrong; the counts describe what the pins declare, not what a reading of each source tree would conclude.

What matters for redistribution is the copyleft tail. The four AGPL members are `iottycloud==0.3.0` (v3, no later-version grant), `pymata-express==1.19`, `pyrecswitch==1.0.2` and `romy==0.0.10`, the last three as `v3 or later` classifiers; AGPL §13 reaches a user who interacts with the program over a network, which is a live question for a home-automation server that serves a web UI, and the corresponding source those terms require is upstream's to provide, not ours. The GPL tail (80) includes `mutagen==1.48.1` and `mysqlclient==2.3.0` (`GPL-2.0-or-later` expressions), and many integration libraries that declare `GPL-3.0-or-later` only through a classifier, such as `python-kasa==0.11.0.1`, `pynobo`, `pyotgw`, `tellcore-py` and `xs1-api-client`. The LGPL tail (28) includes `zeroconf==0.151.5` (`LGPL-2.1-or-later`), `pyvlx==0.2.36` (`LGPL-3.0-or-later`), `python-telegram-bot==22.7` (`LGPL-3.0-only`), `samsungtvws==3.0.6` (`LGPL-3.0`) and `python-gitlab==1.6.0` (a `LGPLv3` classifier). This is an inventory of the pinned requirement set, not of the interpreter's site tree. Names such as `multidict` and `aiosignal` are absent from those files and are resolved by the installer at build time, as are the dependencies that the eighteen extras groups in those pins pull in — `yt-dlp[default]`, `python-kasa[speedups]`, `python-telegram-bot[socks]`, `pygatt[GATTTOOL]` and their siblings — and the install also consults the musllinux wheel index that the image's environment points at (`https://wheels.home-assistant.io/musllinux-index/`, whose wheels Home Assistant builds for platforms PyPI does not serve). Two installed wheels are Home Assistant's own. `home-assistant-frontend==20260930.5` publishes `Apache-2.0`, matching the `LICENSE.md` of its [repository](https://github.com/home-assistant/frontend). `home-assistant-intents==2026.10.6` publishes `Apache-2.0` in its wheel metadata while the [home-assistant/intents](https://github.com/home-assistant/intents/blob/main/LICENSE.md) repository carries `Attribution 4.0 International` (CC-BY-4.0) at its root, and GitHub's license detection for that repository reports CC-BY-4.0. We did not resolve which term governs the sentence datasets inside that wheel, so a recipient who needs certainty about the intent data should read the discrepancy as unresolved and treat CC-BY-4.0's attribution duties as possibly attached to it.

## Notices that must travel

Apache-2.0 §4(d) sends upstream `NOTICE` attributions along with a derivative work. [Home Assistant Core publishes no `NOTICE` file anywhere](https://github.com/home-assistant/core/tree/2026.10.3) — the recursive tree at the pinned tag is 32,348 entries and contains none — so §4(d) sends nothing along from Core itself, and the Apache-2.0 text that §4(a) requires is already inside the image as Core's own installed license file. The PicoTTS source is the opposite case: its built directories (`pico/lib`, `pico/src`, `pico/tts`, `pico_resources`) each hold a `NOTICE` file beside a `MODULE_LICENSE_APACHE2` marker, so the §4(d) obligation has real content for the binary built from them. Whether those `NOTICE` files land in `/usr/local` depends on what that project's `make install` copies, and we have not verified it against the layer contents; whoever builds and conveys that binary carries the obligation, and this flake is not the builder.

Because the copy is digest-preserving, whatever license and notice files upstream placed inside the layers arrive unchanged, and this flake adds, edits and removes none of them. The Alpine userland is the one place where that reassurance is weakest: whether Alpine installs upstream license texts into the rootfs is not verified here, so the per-package index record above may be the only place those terms are written down for a recipient.

Distinguish the acts. Republishing upstream's layers byte-for-byte is a copy of upstream's work under upstream's terms; it is not a derivative work of that code by us, and it creates no obligation to license anything as MIT or to release anything of ours. It is still redistribution, so the terms that condition copies — Apache-2.0 §4, the GPL family's source conditions, CC-BY-4.0's attribution — attach to whoever performs it.

## Conveyance

Fetching at build time conveys nothing: the `skopeo copy` pulls upstream's published layers into the store of the machine that ran the build, and a build on a private machine transfers nothing to anyone. Conveyance begins when that store path leaves the machine — served from a binary cache that others substitute from, `copyTo`'d to a registry or another host's container storage, or `copyToPodman`'d into a local engine on a machine someone else uses. This flake performs none of those acts by itself; `copyTo` and `copyToPodman` are executables an operator runs, and the operator who runs them is the one conveying.

One path is not the operator's: this repository's own CI builds `.#image` and uses flake-lib's `fleet-nix-cache` action, which installs a Nix `post-build-hook` that pushes every built path to the fleet Attic cache. That cache is not a publication. Its endpoint answers `401` to an unauthenticated `GET /main/nix-cache-info`, and substituting from it takes a token the cache's operator issues, so a push there moves the layer bytes within one operator's own trust boundary rather than to anyone else. A cache configured to be pulled anonymously, or any other route by which the built path reaches someone else, is where conveyance begins; nothing this flake states decides which of the two a given cache is. Without a usable token the action configures nothing and pushes nothing, and the run substitutes from the public cache only.

Where a term could not be read it is marked as unverified above rather than assumed permissive.
