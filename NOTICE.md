# Upstream and distributed artifacts

`packages.image` is a copy of upstream's bytes, not a name for them. [flake-lib's `mkOciImage`](https://github.com/jgus-org/flake-lib/blob/e102eb2e5b3f958e8bf23695e60215dcbfc89bfd/lib/mk-oci-image.nix) builds it as a fixed-output derivation running `skopeo --insecure-policy copy --preserve-digests --tmpdir "$TMPDIR" --src-tls-verify=true docker://ghcr.io/home-assistant/home-assistant@sha256:c32ab33f0b0589182b2f40324826acb02a104d1707c91573b6420fd622b82127 dir://$out`, so the output is a Skopeo `dir:` layout holding the platform manifest, the runtime configuration and the compressed layers exactly as published — 22 layers, 659,349,865 bytes compressed, each `application/vnd.oci.image.layer.v1.tar+zstd`, no archive conversion and no rewritten layer — and `copyTo` and `copyToPodman` re-copy that directory with `--preserve-digests`, so the bytes leave the store as they arrived. What follows is whose terms those bytes carry, read from the image's own manifest and configuration blob and from the upstream recipes that produced them at the versions the layers name. No layer was unpacked, so this is an account of what upstream's build records rather than an inventory of the filesystem, and a term that could not be read is marked unverified rather than assumed permissive.

- **What is pinned.** `pin.nix` holds that manifest digest with the recursive Nix hash `sha256-XkWzgAHcciK7CwC3fDH4cz5W5/DP33BBR6ZWutCuA1g=` of the resulting directory. The pinned digest is the `linux/amd64` manifest inside the OCI index (`sha256:407b89cd11a8cb67d388d21739a226c74acbbebe1ac59e3b83b11b43ce76b98f`) that `ghcr.io/home-assistant/home-assistant:2026.10.3` names.
- **What the index holds besides it.** Four entries: the pinned `linux/amd64` manifest, `linux/arm64` (`sha256:c2bb99de7179fe0c192757bc70a53db5f2ded6672a1ced0007accccd3f0de44c`), and two entries whose `platform` is `unknown/unknown`. Those two are not platforms — each is an OCI manifest with `artifactType` `application/vnd.docker.attestation.manifest.v1+json`, a single `application/vnd.in-toto+json` layer annotated `in-toto.io/predicate-type` `https://slsa.dev/provenance/v1`, and a `subject` naming one of the platform manifests, i.e. the build's SLSA provenance attestations. Pinning one platform manifest conveys that manifest and its layers and not the attestations beside it; provenance is pulled from the registry by its own digest.

## Home Assistant Core

- [Home Assistant Core](https://github.com/home-assistant/core) is Apache-2.0: its [`LICENSE.md` at the `2026.10.3` tag](https://github.com/home-assistant/core/blob/2026.10.3/LICENSE.md) is the canonical text, and `pyproject.toml` declares `license = "Apache-2.0"` with `license-files = ["LICENSE*", "homeassistant/backports/LICENSE*"]`. That second path is the PSF text covering backported standard-library code, and those two are the only license texts in the tree — the recursive listing at the tag matches a third name, `script/licenses.py`, which is upstream's own tool for checking dependency licenses rather than a license.
- They travel inside the image: the layer history shows the source copied to `/usr/src/homeassistant` and installed with `uv pip install -e ./homeassistant`, and copies `LICENSE*` and `pyproject.toml` into that tree, so the texts arrive in the installed distribution metadata. Apache-2.0 §4(a)'s duty to give recipients the license is discharged there, not in this repository.
- Upstream's own `org.opencontainers.image.licenses` label reads `Apache-2.0`. That describes Core; everything below is what else is in the image.

## The Python environment

- **How the set was derived.** The core layer installs two requirement files at the in-image paths `homeassistant/requirements.txt` and `homeassistant/requirements_all.txt` — the tag's root files, copied into `homeassistant/` by the build — and home-assistant/docker's own root `requirements.txt` is installed in the base stage by a build-time mount, read there at that repository's tag `2026.10.1` (it publishes no tag at or above that; its `BUILD_FROM` default is the base image the pinned layers record, which ties the recipe to this image). Parsing those three files for `name==version` pins, keeping an extras clause such as `yt-dlp[default]` attached to its name, normalizing case and the `_`/`.`/`-` separators and de-duplicating gives **1,192** distinct distributions: 54 from the root file plus 1,156 from `requirements_all.txt`, less the 21 names both pin, plus the three from docker (`Brotli`, `mysqlclient`, `psycopg2`), whose pins are in the set.
- **Not counted, and why.** `certifi`, `packaging`, `typing-extensions` and `urllib3` are bounded by range rather than pinned, so the installed version is whatever the build resolved. `homeassistant/package_constraints.txt` is a constraint file, not an install input.
- **How the terms were read.** Each distribution's own declaration on PyPI at its pinned version: the `license_expression` field where one is published, otherwise its license classifiers, otherwise the deprecated free-text `license` field. Each distribution is counted once, under the strongest copyleft its declaration states, or under its permissive term when it states none. These are the projects' own claims at those versions, and some are stale or wrong; the counts describe what the pins declare, not what a reading of each source tree would conclude.

- **This is the pinned requirement set, not the site tree.** `multidict` and `aiosignal` are absent from those files and resolved by the installer at build time, as are the dependencies the eighteen extras groups in those pins pull in (`yt-dlp[default]`, `python-kasa[speedups]`, `python-telegram-bot[socks]`, `pygatt[GATTTOOL]` and their siblings), and the install consults the musllinux wheel index the image's environment points at (`https://wheels.home-assistant.io/musllinux-index/`, whose wheels Home Assistant builds for platforms PyPI does not serve). The installed closure is therefore larger than 1,192 and is not enumerated here. The authoritative record of what is installed is each distribution's `*.dist-info/METADATA` under `/usr/local/lib/python3.14/site-packages`, which arrives byte-preserved with the layers.

## Notices that must travel

- Apache-2.0 §4(d) sends upstream `NOTICE` attributions along with a derivative work. [Home Assistant Core publishes no `NOTICE` file anywhere](https://github.com/home-assistant/core/tree/2026.10.3) — the recursive tree at the pinned tag is 32,348 entries and contains none — so §4(d) sends nothing from Core, and the §4(a) license text is already inside the image as Core's own installed file.
- PicoTTS is the opposite case: its built directories (`pico/lib`, `pico/src`, `pico/tts`, `pico_resources`) each hold a `NOTICE` beside a `MODULE_LICENSE_APACHE2` marker, so §4(d) has real content for the binary built from them. Whether those files land in `/usr/local` depends on what that project's `make install` copies, unverified here against the layer contents; whoever builds and conveys that binary carries the obligation, and this flake is not the builder.
- Because the copy is digest-preserving, whatever license and notice files upstream placed inside the layers arrive unchanged, and this flake adds, edits and removes none of them. The Alpine userland is where that reassurance is weakest: whether Alpine installs upstream license texts into the rootfs is not verified here, so the per-package index record may be the only place those terms are written down for a recipient.
- Distinguish the acts. Republishing upstream's layers byte-for-byte is a copy of upstream's work under upstream's terms; it is not a derivative work of that code by us, and it creates no obligation to license anything as MIT or to release anything of ours. It is still redistribution, so the terms that condition copies — Apache-2.0 §4, the GPL family's source conditions, CC-BY-4.0's attribution — attach to whoever performs it.

## Conveyance

- Fetching at build time conveys nothing: the `skopeo copy` pulls upstream's published layers into the store of the machine that ran the build, and a build on a private machine transfers nothing to anyone.
- Conveyance begins when that store path leaves the machine — served from a binary cache others substitute from, `copyTo`'d to a registry or another host's container storage, or `copyToPodman`'d into a local engine on a machine someone else uses. This flake performs none of those acts by itself; those are executables an operator runs, and the operator who runs them is the one conveying.
- One path is not the operator's: this repository's CI builds `.#image` and uses flake-lib's `fleet-nix-cache` action, which installs a Nix `post-build-hook` pushing every built path to the fleet Attic cache. That cache is not a publication: its endpoint answers `401` to an unauthenticated `GET /main/nix-cache-info`, and substituting from it takes a token the cache's operator issues, so a push there moves the layer bytes within one operator's own trust boundary rather than to anyone else. A cache configured to be pulled anonymously, or any other route by which the built path reaches someone else, is where conveyance begins; nothing this flake states decides which of the two a given cache is. Without a usable token the action configures nothing and pushes nothing, and the run substitutes from the public cache only.
